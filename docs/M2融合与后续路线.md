# M1/M2 融合方案与后续开发路线

> 写于 2026-10-03 深夜，依据当晚真机实测。仓库当前：**29 次提交 / tag `v0.1-ondevice-node`**
> 一句话现状：**M1 已在真机跑通**（Node v24.2.0 / platform=openharmony / 端上 HTTP 服务可访问）；
> **M2 只差"让 Node 读到自己需要的文件"这一步**，且根因已定位、正解已确定。

## 一、今晚最后定位到的那条硬规律

**在同一沙箱目录里，"谁写的文件，谁能读"并不成立：**

| 场景 | 写入者 | Node 能否 `require` |
|---|---|---|
| M1 的 `hello.js` | ArkTS `fs.writeSync` | ✅ **能**（已跑通，网页都能访问）|
| M2 的 `bin.js` | OHOS `zlib.decompressFile` | ❌ **不能**（`MODULE_NOT_FOUND`，`requireStack: []`，但 ArkTS 侧 `statSync` 看到 11237 字节、`isFile=true`）|

两者**同目录、同进程、同 uid**，唯一差别是写入者。
⇒ 结论：**鸿蒙解压器产出的文件，对 Node 的 musl 裸 `open()` 视图不可用**。

## 二、M2 正解：让 Node 自己解包（"谁写谁读"必然一致）

```
rawfile/
├─ dsh-payload.tar.gz      ← 载荷（tar.gz 而不是 zip，因为 Node 内置 zlib 能 gunzip）
└─ bootstrap.js            ← ~30 行：gunzip + 极简 tar 解析 + 用 node 自己的 fs 写盘
```
**流程**：
```
ArkTS: resourceManager.getRawFileContentSync('bootstrap.js')
        → fs.writeSync 到 filesDir/bootstrap.js          （M1 已验证这条路通 ✓）
ArkTS: nodeCtl.startBackend({
          script: <filesDir>/bootstrap.js,
          args:   [<filesDir>/dsh-payload.tar.gz, <filesDir>/dsh-v1],
          dataDir: <filesDir>/dsh-harmony-data             （宿主壳会设 DSH_HOME）
        })
bootstrap.js:
        zlib.gunzipSync(tarGz) → 极简 tar 遍历 → fs.writeFileSync 每个文件
        → require(<filesDir>/dsh-v1/node_modules/@deepseek-ai/dsh/lib/bin.js)
          并 process.argv 透传 ['web','--no-open']   （或直接 spawn 同进程 require）
```
**为什么用 tar 不用 zip**：tar 格式只需解析 512 字节头 + 路径前缀，**约 30 行纯 JS**；
zip 需要中央目录 + deflate/存储分支，代码量大得多。Node 内置 `zlib` 直接吃 `.tar.gz`。

**副产品**：`dsh-payload.tar.gz` 体积与 zip 相当（~34 MB），HAP 仍约 158 MB。

## 三、M1 与 M2 的融合设计（一个应用，两条路）

### 3.1 一个应用三种状态（天然自检 + 降级）

```
启动
 ├─ 状态 A：M1 自检页（Node 起来但 DSH 未就绪 / DSH 失败时显示）
 │    显示：platform / arch / node 版本 / execArgv / 三个原生模块加载结果
 │    ⇒ 就是今晚那页，价值极高：一眼看出"是运行时问题还是业务问题"
 ├─ 状态 B：就绪（DSH web 起来，ArkWeb 加载 DSH 页面）
 │    用日志里解析出的【完整 URL（含 ?token=）】加载；端口/token 都不写死
 └─ 状态 C：失败（native 起不来 / 解包失败 / DSH 崩溃）
      日志面板自动展开，并打印 node-boot.log + node-stdout.log 尾部
```

### 3.2 ArkTS 侧的定位（保持不变，这是对的）

ArkTS 只做四件事，**不承担任何业务逻辑**：
1. **引导**：把 rawfile 里的入口脚本写到 filesDir；调 native 启动 Node
2. **观测**：轮询 native 状态 + 从 node 输出里解析 `http://127.0.0.1:<port>/?token=...`
3. **展示**：ArkWeb 加载那个完整 URL；失败时展示日志面板
4. **桥接**（后续）：把手机系统能力（剪贴板/分享/通知/文件选择/相机）经 NAPI 暴露给 Node

### 3.3 需要改的两处

| 改动 | 原因 |
|---|---|
| 「重开」按钮 → **「重新解包」** | `node::Start` 一个进程只能一次 ⇒ 不能重启 node；但**可以重新解包**（下次开进程时用） |
| 启动流程：`ensurePayload` 改为**调 bootstrap.js**（不再用 `zlib.decompressFile`） | 见第二节 |

## 四、后续路线（按优先级）

### M2 收尾（1~2 轮）
1. 造 `dsh-payload.tar.gz`（`tar -czf`，条目 `dsh/...`，无 `./` 前缀）
2. 写 `bootstrap.js`（gunzip + tar 解析 + 写盘 + 进度输出到 stdout）
3. ArkTS 只负责把 `bootstrap.js` 写出来并启动它
4. 起来后：拿 `?token=` 的完整 URL 给 ArkWeb → **应能看到 DSH 的 Web 界面**
5. 首次解包可能 30~90 秒 ⇒ 加进度（bootstrap.js 每 500 个文件打一行，界面透传）

### M3 端上体验（2~3 轮）
- **后台保活**：进程进后台会被**冻结**（今晚实测 `Freeze pid: ... success`）⇒ 需要声明**长时任务**
  （带通知），否则一锁屏 DSH 的会话就停了
- **崩溃自恢复**：`node::Start` 一次性 ⇒ 进程内不可能重启 node
  ⇒ 需要"**进程外看门狗**"（另一个 ability/进程 + 定时器，检测到主进程死则拉起）
- **日志导出**：现在只能截图 ⇒ 加"把 node-stdout.log / node-boot.log 复制到用户可见目录或分享出去"
- **端口/token 固化**：把 DSH 的端口固定下来（`--port`），减少解析依赖
- **工作目录**：DSH 的 workspace 放在沙箱内（`DSH_HOME` 下）；要不要让用户能看到/选择，属产品决策

### M4 上架（1~2 轮）
- 权限与隐私声明一致性（目前只有 `INTERNET`）
- 包体：158 MB（libnode 120 MB + 载荷 34 MB）；如需再小，可考虑首启下载载荷（但违反"离线可用"）
- 图标：用已生成的原创图标
- 签名：切回**发布证书**（`harnessGallery.p7b`）出 app_gallery 包上架
- `.so` 若需自签：`binary-sign-tool.jar`（**在 strip 之后签**）

### M5 长期：**这才是"原生版"真正的价值**
不是"把 PC 的 Harness 搬到手机"✗，而是**让 agent 拥有只有手机才有的能力** ✓：
| 能力 | 实现 |
|---|---|
| 剪贴板读写 | NAPI → `@ohos.pasteboard` |
| 分享/外部打开 | NAPI → `@ohos.app.ability.wantAgent` |
| 通知（让 agent 主动提醒）| NAPI → `@ohos.notificationManager` |
| 文件选择（真实路径）| NAPI → `@ohos.file.picker` |
| 相机/扫码 | NAPI → `@ohos.multimedia.camera` / `scanBarcode` |
| 通讯录/日历 | NAPI → 对应 kit |
| 传感器/定位 | NAPI → 对应 kit |
⇒ 这些通过一个 `dsh-plugin-harmonyos-native` 插件暴露成 DSH 的**工具**，
   agent 就能做 PC 上做不到的事（"帮我把这段话发到微信""扫一下这个码"）。

## 六、今晚的教训（写进习惯）

1. **"能构建"≠"能运行"** —— 必须用**同一份产物**真跑一次（asar unpacked 那个 bug 就是这么抓到的）
2. **"路径存在"≠"能用"** —— `fs.accessSync` 对 0 字节文件/目录也返回 true；
   判据必须是 **`isFile() && size > 阈值`**
3. **"写入者"决定"可读性"** —— 鸿蒙解压器写的文件 Node 读不到；
   **让最终使用者也当写入者**是最稳的设计
4. **自己的日志要打全** —— `argc`/`argv[i]`/入口大小/各候选目录清单，
   这些"看起来啰嗦"的输出，今晚每一个都直接定位了一个 bug
5. **截图是最强通道** —— 沙箱日志连 debug 签名都不让 hdc 读；
   把状态/诊断刷到 UI 上，一张截图胜过十次盲猜
6. **日志面板会截长长数字** —— 少打一位会误导判断（今晚差点误判 36,305,644 为 3,630,564）
   ⇒ 打体积用 `MB` 并保留一位小数，或分段打印

## 一、架构（已验证可用）

```
ArkWeb(Web 组件) ──http://127.0.0.1:5577──► 端上 Node.js(libnode.so)
      │
      └─ libnode_ctl.so (NAPI)  ─ dlopen(libnode.so) → node::Start
         备选: libnode_launcher.so:Main  via childProcessManager.startNativeChildProcess
```
**HAP 布局**：
```
entry/libs/arm64-v8a/libnode.so          ← Node 运行时（真共享库）
entry/libs/arm64-v8a/libnode_ctl.so      ← NAPI 胶水（进程内启动）
entry/libs/arm64-v8a/libnode_launcher.so ← 原生子进程回退
entry/src/main/resources/resfile/<app>/  ← 只读应用包（前端+后端），node 从这跑
<filesDir>/<app>-data/                   ← 可变状态
```

## 二、★★★ 五个必须照做的硬坑（否则必崩）

### 1. `libnode.so` 必须是**真共享库**（`--shared`），不能是 PIE
> `hqzing/ohos-node` 发的是 **PIE 可执行文件**（`ET_DYN` + `PT_INTERP`）却命名为 `libnode.so`。
> `dlopen()` 一个 PIE 进鸿蒙 App，会把 **local-exec `%fs` TLS 别名到宿主 App 的 TLS 块**，
> 于是 V8 的 `thread_local current_per_thread_assert_data` **读到垃圾**，
> release 版 `CHECK AllowHeapAllocationInRelease` 在 `Isolate::Initialize`
> **第一次堆分配时就触发**（崩溃）。

- ✅ 用 `--shared` 构建：PIC + 动态 TLS + `SONAME libnode.so.<vernum>`
- ✅ **下载后校验 ELF**：必须是 `ET_DYN` 且**没有 `PT_INTERP`**
- 现成产物：`electerm/ohos-node-shared` release `ohos-node-shared-v24.2.0`
  （资产 `libnode-arm64.so` / `libnode-x64.so`）

### 2. 启动参数必须带 `--jitless --no-verify-heap`
> `--jitless` 避开 V8 运行时的 `PROT_EXEC` 映射 —— **OpenHarmony 的 W^X 策略会拒绝**，
> 否则在 `node::Start` 里 `SIGTRAP`：`# Check failed: 12 == (*__errno_location())`。
> `--no-verify-heap` 是对受限运行时下分配检查的防御。

### 3. libuv 的 `io_uring` 探测会被 seccomp 杀
> libuv 在 loop init 时**无条件**探测 `io_uring_setup(425)`，**沙箱 seccomp 会 trap 它**。
> 处理：在 `libnode_ctl.c` / `node_launcher.c` 里装 **SIGSYS shim**，
> 把 trap 转成**记录日志后的 `-1`**（**必须正好是 `-1`，不是 `-ENOSYS`**，libuv 的守卫才认）；同时设 `UV_USE_IO_URING=0`。

### 4. `dlopen` / `node::Start` **不能放在 ArkTS UI 线程**
> 内联执行会阻塞 UI 线程到触发 **`APP_INPUT_BLOCK` ANR 看门狗**。
> 处理：`startBackend()` 里开一个 **detached bootstrap 线程**去做 `dlopen` + `node::Start`。

### 5. 子进程回退**比进程内更差**（所以进程内才是主路径）
> 被 spawn 的原生子进程跑在**更严格的 seccomp** 下，**会杀掉 libuv**；
> 而主进程本来就在跑 libuv 类的事件循环（NETSTACK/curl）。
> 处理：进程内为主，子进程仅作**兜底**。

**另加**：装一个**崩溃信号处理器**（把 backtrace + fault PC 写进 `node-boot.log` / hilog，
并**把 node 线程停住而不是让它死掉**）。

## 三、OHOS 原生模块（`.node`）的官方规则

来自 `ohos-npm-ports` 移植指南（原文要点）：

1. **先确认上游有没有 `openharmony` 分支**：看 loader 是否识别 `process.platform === 'openharmony'`、
   有没有发布 `openharmony-arm64` / `linux-arm64*` 产物。
   ★ 这暗示 **OHOS 上 `process.platform` 可能是 `'openharmony'`**（不只是 `'linux'`）
2. **OpenHarmony 产物必须源码构建** —— 「不能用其他平台产物替代 OpenHarmony 目标产物」
3. **未签名的 `.node` / `.so` 装上也用不了**：鸿蒙商用版对 ELF 做**代码签名校验**，
   没有 `.codesign` section 直接不可用 ⇒ 需用带签名支持的 OHOS 工具链，
   或对产物执行 `binary-sign-tool sign -selfSign 1`
4. **OHOS musl 动态链接器不做 lazy binding**：`dlopen` 那一刻**所有未定义符号都必须能解析**，
   缺一个就整体加载失败（不是 glibc 那套"没调用到就不炸"）
5. **dlopen 出来的模块看不到主程序符号**（命名空间隔离）⇒ 链接时加 **`-Wl,-z,global`**
6. **C++ ABI 边界**：调用方与宿主必须同一套 C++ 标准库（都 libstdc++ 或都 libc++），
   mangled name 不同没有编译选项能桥接
7. **Zig 交叉编译选 `aarch64-linux-musl`**，**不要**选 `aarch64-linux-ohos`
   （后者会引用 OHOS libc 没有的 `__emutls_get_address`）
8. 消费方用 npm/pnpm 安装时需额外签名步骤（如 `ohos-signpost` 的 postinstall 钩子）
9. 上游 `package.json` 里的 `packageManager` 字段可能要删掉（避免解析不到对应平台可执行文件）

## 四、Node 交叉编译配方（`hqzing/ohos-node` 的 `build.sh`）

```bash
export CC="$workdir/llvm-19/llvm/bin/aarch64-unknown-linux-ohos-clang   -fno-emulated-tls"
export CXX="$workdir/llvm-19/llvm/bin/aarch64-unknown-linux-ohos-clang++ -fno-emulated-tls"
CONFIGURE_ARGS="--dest-cpu=arm64 --cross-compiling ..."
# OHOS 交叉编译需关闭 Temporal（否则构建失败）
CONFIGURE_ARGS="$CONFIGURE_ARGS --v8-disable-temporal-support"
./configure $CONFIGURE_ARGS
# 产物用 OHOS 工具链签名：
$workdir/ohos-sdk/linux/toolchains/lib/binary-sign-tool sign ...
```
补丁：`0001-fix-argument-list-too-long.patch`、`0002-use-C++20-for-Node.js-core.patch`

**⇒ 若要 `--shared` 版（嵌进 App 用）**：以上配方加 `--shared` 即可（electerm 即如此得到 `libnode.so.24`）。

## 五、构建与签名流程（electerm 的做法）

```
1. prepare-node.sh  下载 libnode-<arch>.so → entry/libs/<abi>/libnode.so（并校验 ELF 是 ET_DYN 无 PT_INTERP）
2. 打前端/后端包     → entry/src/main/resources/resfile/<app>/
3. hvigorw assembleApp          （产出【未签名】的 .app）
4. hap-sign-tool.jar sign-app   （两阶段签名 → 已签名 .app）
```
环境要求：**JDK 21**（`hap-sign-tool.jar` 需要）、**HarmonyOS Command Line Tools 5.0.5.200+**（提供 `ohpm`/`hvigorw`/SDK）
签名材料三件套：`.p12` 密钥库 + `.cer` 证书 + `.p7b` Profile（放 `signing/`）

## 八、★★ 已实测证明：不需要原生 `require-builtin` 插件

这是整个鸿蒙移植方案里**最后的技术风险**，现已从"推断"升级为"实测"。

### 背景
`@deepseek-ai/dsh` 与 `dsh-app-boot` 都依赖原生插件 `node-addon-require-builtin` ✗，
而 OHOS 的原生模块**必须源码构建 + 签名**（官方移植指南明说"不能用其他平台产物替代"）✗
—— 一度看起来是必须填的坑。

### 转机：调用方本来就是"双重兜底"
```js
// cordis-plugin-loader/lib/index.js
if (process.execArgv.includes("--expose-internals"))
    try { return require(id); } catch {}                                 // ★ 纯 Node 路径
try { return require("node-addon-require-builtin").requireBuiltin(id); } catch {}  // ★ 且被 try 包住
```

### 实测结果（本机 Node v24.21.0）
| 实验 | 结果 |
|---|---|
| 纯 JS 桩 + `--expose-internals`，对 5 个内部模块调 `requireBuiltin` | **11/11 全通过** ✓ |
| 同一桩**不带**该 flag | 5 个内部模块**全部** `MODULE_NOT_FOUND` ✗ ⇒ **flag 是必需的** ✓ |
| 复刻 DSH 真实写法 `loadInternal()` | `internal/modules/cjs/loader` → OK（16 项导出）✓；`internal/modules/esm/loader` → OK（4 项导出）✓ |
| 这 5 个内部模块在 **Node v24.2.0**（OHOS 用的版本）里 | **全部存在** ✓（42,587 / 69,120 / 13,169 / 13,997 / 39,009 字节）⇒ 版本差**不影响**这条路 ✓ |

用到的 5 个内部模块（抄自 `dsh-app-boot` 的 `internalModules()`）：
```
internal/modules/esm/loader
internal/modules/cjs/loader
internal/modules/helpers
internal/modules/esm/utils
internal/modules/esm/resolve
```

### 落地结论
1. 启动参数**必须**含 **`--expose-internals`**（已写进 `launch.json` 与宿主壳 ✓）
2. 把 `node-addon-require-builtin` **替换为 ~20 行纯 JS 桩**（`tools/make-ohos-runtime-manifest.mjs` 会自动生成 overlay ✓）
3. **不需要**为 OHOS 编译任何原生模块 ✓✓ —— 原生工作量为 0

# Harness on HarmonyOS —— 技术落地方案 **v0.4**

> **版本演进**
> - v0.1 猜想：需要移植 5 个原生模块 → 风险高
> - v0.2 实测：核心不依赖 Electron；DSH 是「接口 + 多实现」架构
> - v0.3 实测：原生模块全部 Windows-only + 懒加载，鸿蒙不加载
> - **v0.4 定案**：`node-addon-require-builtin` **也不需要移植** —— 代码里有
>   `if (process.execArgv.includes("--expose-internals")) return require(id)` 的**纯 Node 路径**，
>   且原生化调用被 `try/catch` 包住 ⇒ **启动时带 `--expose-internals` + 一个 10 行 JS 桩即可** ✓
>   ⇒ **原生移植工作 = 0**；难点只剩「NAPI 宿主壳 + 打包 + 签名」，全部有已上架先例
>   另附：[参考实现-构建要点.md](参考实现-构建要点.md)（从已上架应用逆向的配方 + 5 个必崩硬坑）

---

## 1. 目标与验收

**目标**：手机上装一个 App，点开即用 —— Agent 运行时、模型调用、工具执行、会话数据**全在手机本地**。

| 档位 | 标准 |
|---|---|
| **M1 骨架** | 端上 Node 起得来并输出 HTTP 服务；ArkWeb 能打开它的界面 |
| **M2 可用** | 新建会话 / 发消息 / 模型返回 / 读写文件 / 执行命令 / 会话持久化 |
| **M3 对齐桌面** | 插件体系完整加载、工作区/终端/文件预览、设置齐全、冷启动 < 10s、可上架 |

### 2.3 核心不依赖 Electron
```
asar 内 436 个 package.json：没有任何一个声明 electron 依赖
Electron 只在"外壳/前端资源"（5 MB / 352 MB 解压总量）
```

### 2.4 ★ 原生模块全部「Windows-only + 懒加载」—— 鸿蒙上不会加载
| 包 | 声明依赖 | 实测运行时行为 |
|---|---|---|
| `dsh-fs-local` | koffi | 仅在 `lib/types/win32.js` 内 `await import("koffi")`；注释：*"Koffi loads lazily so non-Windows processes never open Win32 libraries"*；主体用 `node:fs/promises` ✓ |
| `dsh-subprocess-local` | koffi, node-pty | koffi 仅 Win32 路径；**node-pty 是 `createLazyRequire("node-pty")`**（终端功能才加载）✓ |
| `dsh-session-persistence-jsonl` | koffi | 注释：*"Load the small Win32 API lazily so non-Windows processes never load Koffi"* ✓ |
| `dsh-host-directory-picker-native` | koffi | Win32 COM 对话框专用 ⇒ **改用已有的 `…-auto` / `…-browse`**（零代码）✓ |
| `dsh-sandbox-windows-acl` / `dsh-win32-process` | koffi | **Windows 专属插件** ⇒ 鸿蒙不加载 ✓ |
| `dsh-attachment-local` | sharp | `lib/index.js` 内**0 处**原生引用 ⇒ 懒加载/可选 ✓ |
| `dsh-experimental-speech-to-text-sensevoice` | sherpa-onnx | 实验性插件，可停用 ✓ |

### 2.5 ★★ 唯一硬需求 T1 已有官方 musl-arm64 二进制
`node-addon-require-builtin`（`@deepseek-ai/dsh` 与 `dsh-app-boot` 的必需依赖）
```
加载器 node-addon-native-custom-loader 的规则：
  NAPI_VERSION = '9'（N-API v9 → ABI 稳定，跨 Node 大版本可用）
  平台后缀：darwin-<arch> | linux-<arch>-<libc> | win32-<arch>-msvc | <platform>-<arch>
  子包名  ：<前缀>-<后缀>
npm 实测：
  ✓ node-addon-require-builtin-linux-arm64-musl   ← ★ OpenHarmony 用的就是 musl
  ✓ …-linux-x64-musl    ✗ …-linux-arm64-glibc    ✗ …-openharmony-arm64
干预手段：NARB_BACKEND / NARB_NATIVE_CACHE_DIR / NARB_DISABLE_OPTIONAL_PACKAGE / NARB_DISABLE_LOCAL_BUILD
```
**★ v0.4 更正**：官方移植指南明确「OpenHarmony 产物必须源码构建 + 必须签名，不能用其他平台产物替代」✗
⇒ v0.3 的"直接复用 musl 二进制"假设**不成立**。

**但实测发现：根本不需要它** ✓✓
```js
// cordis-plugin-loader/lib/index.js —— 双重兜底
if (process.execArgv.includes("--expose-internals"))
    try { return require(id); } catch {}                                 // ★ 纯 Node 路径
try { return require("node-addon-require-builtin").requireBuiltin(id); } catch {}  // ★ 且被 try 包住
```
- `dsh-app-boot` 里也只在 `internalModules()` 内 `require` 它
- ⇒ **启动 Node 时带 `--expose-internals`**，`require('internal/...')` 直接可用 ✓
- ⇒ 再放一个 **~10 行 JS 桩**（`requireBuiltin: id => require(id)`，`isAllowedInternalId: () => true`）彻底替代 ✓
- ⇒ **T1 = 0 原生工作** ✓✓

### 2.8 ★ 新增风险：Node 版本差（24.2.0 vs 24.18.1）
- DSH 官方运行包声明 **`nodeVersion: 24.18.1`**（清单 `release` 字段）
- 现成**可嵌入**的 `libnode.so`（`electerm/ohos-node-shared`）是 **24.2.0** → **低一个身位** ✗
- `hqzing/ohos-node` 有 **v24.21.0**，但是 **PIE 可执行** ✗（dlopen 会因 TLS 别名冲突崩 V8，见参考文档）

**两条出路**：
1. **先试 24.2.0**：若 DSH 未用到 24.3+ 的 API 即可用（成本最低；需实测）
2. **自建 `--shared` 的 24.18.1 / 24.21.0**：用 `hqzing/ohos-node/build.sh` 的配方
   （llvm-19 `aarch64-unknown-linux-ohos-clang -fno-emulated-tls` + `--cross-compiling`
   + `--v8-disable-temporal-support` **再加 `--shared`**）→ 需一台 Linux x64 主机（阿里云可）
   ⇒ **这是可控的范围**（同一份源码，只多一个 configure 开关）

## 4. 架构与最小改造集

```
┌──────────────── HarmonyOS App (HAP) ────────────────┐
│ ArkTS 外壳                                          │
│  ├─ NodeHost(NAPI,C++) dlopen(libnode.so)→node::Start│
│  │     stdout/stderr → <filesDir>/node-boot.log      │
│  │     崩溃自重启；备选 nativeChildProcess            │
│  ├─ ArkWeb → http://127.0.0.1:PORT （DSH web UI）    │
│  └─ 内建日志库 + 被动采样（复用已实现的设计）          │
│ libs/arm64-v8a/libnode.so                            │
│ resfile/dsh/  ← 按 desktop-runtime.json 裁剪的运行包   │
└──────────────────────────────────────────────────────┘
```

| # | 改造项 | 结论 | 量级 |
|---|---|---|---|
| **T1** | `require-builtin` | **`--expose-internals` + 10 行 JS 桩**，无需原生 ✓ | **0** ✓ |
| **T2** | 文件系统 | koffi 懒加载 ⇒ **`dsh-fs-local` 原样可用** | **0** ✓ |
| **T3** | 子进程 / 终端 | node-pty 懒加载 ⇒ 基本可用；PTY 若要可后续补 | **0~小** ✓ |
| **T4** | 目录选择器 | 配置 `…-auto` / `…-browse` | **0** ✓ |
| **T5** | 停用 win/实验插件 | `sandbox-windows-acl`、`win32-process`、语音 | **0** ✓ |
| **T6** | 附件图像 | sharp 懒加载 ⇒ 原样可用（缩略图可能降级）| **0~小** ✓ |
| **T7** | 运行包裁剪与生成 | 依 `desktop-runtime.json` 生成 OHOS 清单 | 中 |
| **T8** | 签名 / 打包 | `ohos-signpost` + 照 electerm 组织 HAP | 小 |
| **T9** | **NAPI 宿主壳** ★ | 照 electerm：`libnode_ctl`（**detached 线程**里 dlopen + node::Start）+ `--jitless` + io_uring SIGSYS shim + 崩溃处理器 | **中 ← 主战场** |
| **T10** | **启动参数与 shim** | `--expose-internals --jitless --no-verify-heap`；`UV_USE_IO_URING=0`；require-builtin 桩 | 小 |

**结论：原生移植 = 0；工程 = T9（宿主壳）+ T7（打包）+ T8（签名），全部有已上架先例。**

## 6. 分阶段计划

### M0 可行性闸门（0.5~1 天，不写鸿蒙代码）
- V1（纯 Node 启 web 服务，**沙箱化**：独立 DSH_HOME + 独立端口）
- 产出：**《可行性结论 + 残余改造确认表》** → 决策 B / A

### M1 骨架（2~4 天）
- 鸿蒙工程 + `entry/src/main/cpp` + `libnode_ctl` NAPI 壳
- 先跑 `hello.js` → 写 `<filesDir>/node-boot.log`（证明嵌入成功）
- ArkWeb 打开本机端口
- 产出：**手机上启动 Node 并显示它的网页**

### M2 跑起 DSH（3~6 天，比 v0.2 预估缩短）
- 按清单裁剪运行包 → `resfile/dsh/`
- 放入 T1 的 musl-arm64 二进制；配置 T4/T5
- 跑通：新建会话 / 发消息 / 模型返回 / 读写文件 / 执行命令
- 产出：**手机上能真实对话的 Harness**

### M3 对齐 + 上架（1~2 周）
- 插件完整、终端/工作区/预览、冷启动优化、前后台与崩溃恢复、日志诊断
- 签名、隐私声明、AGC 上架
- 产出：**可上架的 Harness for HarmonyOS**
